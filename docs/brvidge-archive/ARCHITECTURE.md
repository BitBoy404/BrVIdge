# Предлагаемая архитектура BrVIdge

Статус: проект архитектуры, Phase 3. **Ни один модуль не реализован.**
Конкретные решения могут измениться после прототипов Phase 4.

---

## 1. Отправные предположения

1. Гостевой код — x86-64 (AMD Zen 2). Хост — x86-64. Инструкции CPU
   выполняются нативно: декодер/рекомпилятор x86 **не нужен**.
2. Графический интерфейс консоли — DirectX 12 в варианте консольного
   `d3d12_xs.dll` (`D3D12.X`). На хосте доступен D3D12: нужен слой
   совместимости объектов и команд, а не софтверный рендерер.
3. Шейдеры — машинный код RDNA2 в консольных контейнерах. Их нужно
   декодировать и перевести в DXIL (SM 6.6+).
4. Игра использует системные API Xbox (kernelx, XGameRuntime, XAudio2,
   GameInput, DirectStorage) и виртуальные диски. Их реализует HLE-слой.
5. Игровые данные недоступны легально → всё разрабатывается и тестируется
   на синтетических фикстурах.

## 2. Общая схема

```text

                                           │
                       ┌───────────────────▼─────────────────────┐
                       │            brv_runtime                    │
```

## 3. Поток выполнения (проектируемый)

1. `brv run <exe> [--console series-x|series-s]` читает конфиг из `data/`,
   проверяет среду (Windows, SM 6.6, mesh shaders, DXC, RAM/VRAM).
2. `brv_pe` анализирует PE32+: секции, релоки, импорты/экспорты, TLS.
3. `brv_loader` отображает образ в процесс, применяет релоки, связывает
   импорты через resolver, регистрирует TLS и обработчик исключений.
4. Resolver для каждого `dll!function`:
   1. реализация в `brv_hle` (имеет приоритет);
   2. экспорт системной DLL Windows (если `HostPolicy` разрешает);
   3. экспорт DLL, поставляемой вместе с игрой;
   4. явная заглушка с записью в отчёт (`trap`/`zero`).
5. Потоки игры создаются как потоки Windows с заданными приоритетами
   и affinity; примитивы синхронизации переводятся в хост-аналоги.
6. При создании D3D12.X-объекта `brv_gpu` подменяет его своей обёрткой
   с консольной раскладкой полей; записи консольного списка команд
   интерпретируются в доступные D3D12-команды.
7. При создании PSO `brv_shader` декодирует консольный шейдер, строит SSA IR,
   структурирует EXEC, трассирует ресурсы, транслирует в HLSL → DXIL
   (или напрямую в DXIL) и кэширует результат по content hash.
8. PresentX-эмуляция показывает кадр в окне; frame pacing отдельно.
9. `brv_diag` пишет log/report, профили CPU/GPU, обрабатывает сбои.

## 4. Обоснование необходимости модулей

Это ответ на список предполагаемых компонентов из задания. «Не нужен»
означает: модуль с таким назначением создаваться не будет.

| Предложенный модуль | Решение | Обоснование |
|---|---|---|
| Executable Analysis | **нужен** | PE32+/COFF-анализ необходим для loader и диагностики |
| Instruction Decoder (CPU x86) | **не нужен** | гость и хост — x86-64, инструкции выполняются нативно |
| Instruction Decoder (GPU RDNA2) | **нужен** | основа GPU-трансляции; таблицы из MIT-источника AMD |
| Static Recompiler (CPU) | **не нужен** | бессмысленно перекомпилировать x86-64 в x86-64 |
| Static Recompiler (данные) | **нужен как AOT** | предварительный разогрев кэша шейдеров/текстур, не замена JIT |
| Dynamic Recompiler (CPU) | **не нужен** | см. выше |
| Dynamic Recompiler (GPU shaders) | **нужен** | трансляция при создании PSO и шейдеров, загружаемых во время выполнения |
| Runtime Execution | **нужен** | главный цикл, порядок инициализации, управление жизненным циклом |
| Thread Management | **нужен (минимально)** | приоритеты, affinity, ограничение пула фоновых потоков; собственный планировщик не нужен |
| Graphics Translation | **нужен** | D3D12.X-объекты и команды → host D3D12 |
| DirectX 12 Backend | **нужен** | прямой бэкенд без промежуточного движка |
| Shader Translation | **нужен** | RDNA2 → DXIL |
| Shader Cache | **нужен** | content-addressed, ключ включает версию транслятора и DXC |
| GPU Resource Management | **нужен** | размещение в UMA, жизни дескрипторов, бюджет VRAM |
| Pipeline Management | **нужен** | PSO, root signatures, фоновое создание с stand-in |
| Runtime Loader | **нужен** | см. `brv_loader` |
| System API Compatibility | **нужен** | ядро подхода HLE |
| Memory Management | **нужен** | guest VA/UMA/4 GiB-окна/бюджет |
| Filesystem Compatibility | **нужен** | виртуальные диски, overlay, без изменения папки игры |
| Audio Backend | **нужен** | XAudio2-совместимый shim, PCM + доступные кодки |
| Input Backend | **нужен** | GameInput/XInput + клавиатура/мышь |
| Debugger | **нужен в минимальном виде** | точки останова, дампы памяти, символические имена module+RVA |
| Logging System | **нужен** | обязательный компонент с первого прототипа |
| Performance Profiler | **нужен (базовый)** | таймеры CPU/GPU, счётчики кэша, отчёт |
| Compatibility Diagnostics | **нужен** | таблица покрытия API, `report.json`, честные `SKIPPED` |
| Configuration Manager | **нужен** | TOML, профили Series X/S, проверка среды |

## 5. Описание модулей

### 5.1 brv_common, brv_config, brv_log

- Единые типы ошибок и `Result`, little-endian reader, hex dump.
- Конфигурация TOML: пути, профиль консоли, лимиты памяти/потоков, включение
  диагностики. Значения по умолчанию консервативны для 8 ГБ VRAM.
- Логирование с уровнями и файловым выводом в `data/logs/`.
- **Не реализовано.**

### 5.2 brv_pe и brv_loader

- Только чтение и отображение PE32+: секции, релоки, импорты по имени/ ordinal,
  delay-load, TLS, таблицы исключений, экспорты.
- Поддержка собственных DLL title и псевдо-handle для консольных DLL.
- Crash reporter: имя модуля + RVA, unwinding стека, `crashes.log`.
- **Не реализовано.**

### 5.3 brv_memory

- Guest virtual address space с разрешёнными/запрещёнными регионами.
- UMA-область, доступная CPU и GPU без копирования; окна 4 GiB;
  first-fit allocator; учёт \"физических страниц\" консоли.
- Бюджет: по умолчанию 4–6 ГБ host UMA под текущий рабочий набор,
  не полные 16 ГБ. Точные значения — после профилирования Phase 7–8.
- **Не реализовано.**

### 5.4 brv_hle

- Реализации kernelx, XGameRuntime (offline XUser/XGameSave/XPackage/XSystem),
  файловых API, DirectStorage-очередей, XAudio2, GameInput.
- Виртуальные диски `GAME:`, `G:`, `D:`, `S:\`, `T:\` → папки пользователя,
  записи идут в overlay.
- Resolver и политика хост-pass-through; все неподдерживаемые вызовы
  фиксируются в отчёте; сетевые вызовы отклоняются и логируются.
- **Не реализовано.**

### 5.5 brv_gpu

- Обёртки над D3D12-объектами с консольной раскладкой полей (чтобы гостевой
  код безопасно писал в «свои» структуры).
- Интерпретатор записей консольного списка команд: сначала compute
  (по образцу publicly описанного BVH-билдера), затем графические записи.
- Управление PSO, root signatures, дескрипторными кучами, PresentX и frame pacing.
- Приоритет корректности: неподдерживаемая команда → логирование и безопасный отказ,
  не сброс драйвера.
- **Не реализовано.**

### 5.6 brv_shader

- Декодер RDNA2 на основе machine-readable ISA (MIT).
- SSA IR по одной machine instruction на операцию; structurization EXEC
  в per-lane boolean; трассировка дескрипторов до root parameter.
- Поддержка: VS/PS/CS/MS(NGG)/GS, atomics, LDS, image/sampler, wave ops,
  BVH-инструкции — по мере появления синтетических тестов.
- Бэкенд: HLSL → DXC как основной на первом этапе; прямой DXIL —
  как платформо-независимая альтернатива после проверки coverage.
- Дифференциальные тесты: консольная программа и её эталон дают одинаковые
  регистры/память.
- **Не реализовано.**

### 5.7 brv_formats, brv_audio, brv_input

- Тайлинг GFX10, BCPack, XMA/Opus по открытым спецификациям; только
  проверяемые синтетические эталоны.
- Звук: PCM и доступные кодки; XMA/Opus как отдельные задачи.
- Ввод: XInput-геймпад, клавиатура/мышь как замена.
- **Не реализовано.**

### 5.8 brv_diag

- Логи, трассировка вызовов API, дампы памяти/кадров, GPU timing (Pix/RenderDoc
  совместимость через нативный D3D12), таблица покрытия API.
- Job Object с лимитом памяти для изоляции DXC и гостевого кода.
- **Не реализовано.**

## 6. Ключевые архитектурные решения

| Решение | Альтернатива | Почему выбрано |
|---|---|---|
| Native x86-64 + HLE | CPU-эмуляция | Нет накладных расходов, проверено VIctory/XCL |
| D3D12 как бэкенд | Vulkan | На Windows D3D12 нативен; меньше слой трансляции |
| HLSL→DXC сначала, прямой DXIL позже | только прямой DXIL | DXC даёт проверенный путь; прямой DXIL снимет latency/OOM, но требует больше работы |
| Трансляция при создании PSO + AOT-разогрев | только AOT | Шейдеры могут грузиться динамически; AOT — лишь ускорение |
| Виртуальные диски + overlay | прямой доступ к папке игры | игры строят консольные пути; запись не должна портить файлы |
| log-first stub | сразу «тихие» нули | Нужно знать реальный вызов, прежде чем его реализовывать |
| WARP как диагностика | всегда реальный GPU | Риск сброса драйвера на некорректных командах |
| Clean-room | копирование кода XCL/VIctory | лицензии несовместимы (GPL-2-only vs GPL-3-or-later) |

## 7. Бюджет ресурсов целевой машины

| Ресурс | План | Комментарий |
|---|---|---|
| VRAM 8 ГБ | до ~4–5 ГБ под рабочие текстуры/RT/BVH, остальное — swap/streaming | Экономия важнее максимального качества |
| Host RAM 32 ГБ | 4–6 ГБ UMA, 2–4 ГБ под DXC/кэш, остальное — ОС и игра | Контроль Commit и page file |
| CPU 6 ядер | игровые потоки — приоритет; транслятор — 2–3 фоновых потока; DXC — отдельный процесс | Не «перегружать» планировщик |
| Disk | контент-адресуемый кэш шейдеров/текстур в `data/cache` | Ключ включает версии транслятора и DXC |
| Сеть | offline | Все online-вызовы отклоняются |

## 8. Явные не-цели

- Поддержка других игр на initial этапе.
- Эмуляция Xbox 360/Xbox One.
- Работа с шифрованными пакетами XVC/MSIXVC, ключами, DRM.
- Собственный x86-64 JIT/дизассемблер.
- Софтверный рендеринг как основной режим (только WARP для диагностики).
- Любые обещания совместимости без протокола тестирования.

## 9. Что считается «реализованным модулем»

Модуль считается реализованным, когда одновременно выполняются:

1. есть исходный код с комментариями на русском;
2. есть модульные тесты на синтетических данных;
3. есть документация контракта и ограничений;
4. он честно сообщает о неподдерживаемых случаях;
5. сборка и тесты проходят в чистом окружении.

До этого все модули помечаются как **не реализовано**.
